# Log Taxonomy for Embedded Infotainment Systems

## Purpose of Log Taxonomy
A well-defined log taxonomy is essential for systematic log-based analysis.
In embedded infotainment (IVI) systems, logs are heterogeneous, distributed,
and generated across multiple software layers. This taxonomy provides a
structured classification of logs to support failure prediction and diagnosis.

The taxonomy serves as a foundation for log preprocessing, feature extraction,
and diagnostic reasoning within the proposed framework.

## Log Classification Dimensions
Logs in embedded IVI systems are classified based on multiple dimensions,
reflecting both software architecture and operational context.

---

## 1. Classification by Software Layer

### 1.1 System-Level Logs
Generated by the operating system and low-level services.

**Examples:**
- Kernel messages
- Scheduler events
- Memory allocation and CPU usage
- Device driver messages

**Relevance:**
Indicates resource exhaustion, timing issues, and hardware–software interactions.

---

### 1.2 Middleware-Level Logs
Generated by communication frameworks and service layers.

**Examples:**
- Inter-process communication (IPC) logs
- Service discovery failures
- Message queue overflows
- Network and bus communication events

**Relevance:**
Useful for diagnosing service interaction failures and latency issues.

---

### 1.3 Application-Level Logs
Generated by IVI applications and user-facing services.

**Examples:**
- Application startup and shutdown
- UI crashes or freezes
- Media playback errors
- Navigation and connectivity events

**Relevance:**
Reflects functional failures visible to end users.

---

## 2. Classification by Log Severity

### 2.1 Informational Logs
Normal operational messages describing system behavior.

**Examples:** Initialization messages, status updates

---

### 2.2 Warning Logs
Indicate abnormal but recoverable conditions.

**Examples:** Resource threshold warnings, retry attempts

---

### 2.3 Error Logs
Represent software faults or failed operations.

**Examples:** Failed API calls, exception traces

---

### 2.4 Critical Logs
Indicate severe failures requiring immediate attention.

**Examples:** System crashes, watchdog resets, kernel panics

---

## 3. Classification by Temporal Characteristics

### 3.1 Event-Based Logs
Discrete events triggered by specific system actions.

**Examples:** Function calls, state transitions

---

### 3.2 Periodic Logs
Logs generated at fixed time intervals.

**Examples:** Heartbeat signals, performance monitoring logs

---

### 3.3 Burst Logs
High-frequency log bursts occurring during abnormal behavior.

**Examples:** Repeated error messages before a crash

---

## 4. Classification by Failure Association

### 4.1 Pre-Failure Logs
Logs that appear before a failure occurs.

**Purpose:** Early failure prediction

---

### 4.2 Failure-Time Logs
Logs generated at the moment of failure.

**Purpose:** Failure detection and confirmation

---

### 4.3 Post-Failure Logs
Logs recorded after recovery or restart.

**Purpose:** Root cause diagnosis and recovery analysis

---

## 5. Classification by Structural Format

### 5.1 Structured Logs
Logs with fixed formats and predefined fields.

**Examples:** JSON, key–value pairs

---

### 5.2 Semi-Structured Logs
Logs with partial structure.

**Examples:** Tagged messages with free text

---

### 5.3 Unstructured Logs
Free-text logs without consistent format.

**Examples:** Debug print statements

---

## Mapping to Framework Components
The proposed log taxonomy supports the framework as follows:
- Log collection & ingestion: Identifies log sources and formats
- Preprocessing & normalization: Guides parsing and structuring strategies
- Feature extraction: Determines relevant attributes per log category
- Failure prediction: Focuses on pre-failure and warning patterns
- Root cause diagnosis: Links failure-time and post-failure logs to causes

## Summary
This log taxonomy provides a systematic foundation for analyzing embedded IVI
logs. By classifying logs across multiple dimensions, the taxonomy enables
structured processing, improved explainability, and effective failure prediction
and diagnosis within the proposed framework.
